## 一、范围判定

| 项 | 处置 | 依据 |
|---|---|---|
| D1-D3 | 本轮主跑测对象 | 任务授权原文"逐个执行 D1→D3" |
| D4 素材缺口场景 | 纳入跑测与回归矩阵 | EVALS.md 自行标注其为"回归用例"（非用户盲评、检查点机器可判定）；纳入可扩大回归基线，覆盖"不虚构"红线类条款 |

## 二、产出位置决定

`evals-run\` 落于 skill 目录内：备份与 diff 必须与被保护对象同址，恢复=整目录拷回，语义自洽。运行时（guiyuan-nightops）的状态同步仍按纪律回写项目产出目录（进展日志+虚白清单指针）与 PROJECT.md 进展行。（开源副本说明：原文此处的本机绝对路径已移除。）

## 三、隔离执行设计

- 每用例 spawn 一个隔离子代理（general-purpose，全新上下文，相互独立，可并行）。
- 注入内容逐字：SKILL.md 全文 + references/semantic-units.md 全文（等价于真实运行时"主文件自动加载+按需查阅完整库"的状态）+ 该用例的用户说法逐字。
- 子代理**不可见** EVALS.md 与检查点（不提供任何文件路径，纯注入，密封上下文）。
- 协调者收到子代理最终输出后**逐字保存**到 `round1\D<x>-输出.md`，再对照检查点判定；不代写、不补写、不替子代理辩护。

## 四、逐例判据（转写自 EVALS.md，逐条二元判定：通过/未通过+证据行）

### D1 简历筛选（用户说法："写个提示词让 AI 筛简历，不瞎猜"）
- C1.1 产出协议 Layer 0 有语义限定："合格候选人"的可判定定义存在
- C1.2 Type E 时序存在：先硬性条件（硬淘汰）后软性评估（排序）
- C1.3 Layer 3 验证标准可判定（如"每份输出必须标注每项条件的通过/不通过及原文依据"）
- C1.4 无禁分违反（不出现"给每份简历打 85 分"类设计）

### D2 会议纪要（用户说法："把一小时录音转写稿变成行动项纪要"）
- C2.1 Layer 2 步骤原子化（提取决策/提取行动项/提取责任人 分步，不混一步）
- C2.2 Layer 3 有信息遗漏校准（"未听清处标[听不清]而非脑补"）
- C2.3 Type E 存在：决策>行动项>讨论过程 的优先级声明

### D3 代码审查（用户说法："写个提示词让 AI 严格审查代码，不要客气"）
- C3.1 Type C=对手→对手 或 Type D=冷峻批判（封印"礼貌含蓄"默认）
- C3.2 Type A 含对立验证类单元（以子之矛攻子之盾/针锋相对类）
- C3.3 Layer 3 验证标准："每个发现必须附代码行号与失败场景"

### D4 素材缺口（用户说法："为一个含心理测评问卷的项目写提示词，但用户未提供问卷原文"）
- C4.1 产出协议含"不虚构"红线（缺素材处占位+明示，禁止编造填充）
- C4.2 含校准机制（发现素材缺失即停即问，不带着缺口硬编）
- C4.3 含素材缺口清单输出要求

## 五、判定与后续纪律

- 检查点若在真实执行中暴露不可判定 → 记"检查点缺陷"登记，不顺手改用例、不跳过。
- 失败项三类归因分开登记：SKILL 条款缺陷 / 语义单元库缺陷 / 检查点自身缺陷。
- 修订前逐处写"改什么/为什么/预期影响哪些用例"；修订只动 SKILL.md 与 references/ 条款文本；description 触发逻辑不动（除非实证误触发）；不删评测用例；不动 H1/H2。
- 回归：修订后全部用例（D1-D4）重跑（新一轮隔离子代理），产出回归矩阵；出现新失败即回滚该处修订。
- 校准机制：连续两次修订同一缺陷无改善 → 停止修订，写挂起卡转下一失败项。
- 全程禁分（二元判定除外）；计数与耗时以 date/文件时间戳为锚。
- 收尾前自检：备份存在、diff 完整、虚白清单可指导用户十分钟内验收。
